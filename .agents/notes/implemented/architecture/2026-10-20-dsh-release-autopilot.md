# Agent Note: dsh-release-autopilot

Status: implemented

## Problem

上游 dsh 新版本的「发现」与「机械适配」已有脚本（dsh-watch / dsh-adapt / dsh-rehearse），但发现到发布之间仍靠一次人工会话：克隆、适配、push、开 PR、等 CI、合并适配 PR、等 release-please 版本 PR、合并、派发 build、核验资产。6h SLA 的成败因此取决于人是否在场，定时器只能报警不能收尾。需要一条可装进 systemd timer、默认全自动、失败可观测且可安全中断的命令。

## Decision

新增 `scripts/dsh-release-autopilot.mjs`（npm `dsh:autopilot`）作为编排器，默认 ①–⑧ 全自动：dsh-watch --dry-run --json 探测（无新版打印「无需适配」exit 0，不开单）；`git clone --local --shared` 到 /tmp 并 fetch GitHub main，临时 runtime 由 `dsh-rehearse --scenario install --version <target> --keep --json` 准备（复用它、不重写安装；再读一次包版本自证），克隆里跑 `dsh-adapt`；只提交 `git status --porcelain=v1 -z` 里已跟踪、非 KANBAN 的文件，commit 为 `fix(dsh): 适配上游 dsh <target>（autopilot）`，push `auto/dsh-<target>`（既有分支才 `--force-with-lease=refs/heads/...:<远端 sha>`）；`gh pr create` 正文带 target/verdict/门禁数/耗时/自动生成声明与 `<!-- dsh-autopilot: ... -->` 标记。等 CI 用 `gh pr view --json statusCheckRollup`（本机 gh 2.45 没有 `pr checks --json`）；SUCCESS/SKIPPED/NEUTRAL 视为非失败，明确 FAILURE/CANCELLED/TIMED_OUT/ACTION_REQUIRED 与 pending 超时一律不合并。合并固定 `gh pr merge --squash --admin`，`mergeable=CONFLICTING`/`DIRTY` 立即停，任何路径都不对 main 发起写或 force。版本 PR 等 `chore(main): release X.Y.Z` ≤15 分钟：release-please 的 bot PR 在 GitHub 上结构性地不跑 workflow（statusCheckRollup 恒空），所以替代门禁是 MERGEABLE + head 必须以 release-please--branches-- 开头 + 变更文件全在写域白名单（三处版本文件/Cargo.lock/CHANGELOG/.release-please-manifest.json/KANBAN）+ 若真有 check 必须非失败；零 check 时先等两个轮询周期的静默期，并在日志与文档明写「按 bot PR 例外合并」，不假装 checks 绿。随后从标题解析 tag，等 Release 出现（≤10 分钟），只有 `total_count==0` 才 `gh workflow run build.yml --ref vX.Y.Z`（已有运行不重复派发，避免 cancel-in-progress 取消在跑构建），最后轮询资产 ≥3（≤30 分钟）。幂等靠 `gh pr list --state all --head auto/dsh-<target>`：OPEN 复用、MERGED 从 ⑥ 续走、CLOSED 才重新适配；最新 Release 正文记录的 dsh latest/next == target 且资产 ≥3 时直接 exit 0「已发布」；issue 评论按内容 sha256 去重。`--dry-run` 只探测+打印计划；`--stage1` 停在 ⑤ 之后；`--require-canary` 在 ⑤ 之前跑 `dsh-adapt --canary`，缺真实 dev 日志或断言失败 ⇒ exit 3、回帖「等真机验收」、PR 保持打开。`--issue` 缺省按 target 词边界在 open 的 dsh-upgrade/sla-breach 里找，找不到才新建（assignee + @ 提及）。退出码 0/1/2/3。GH_BIN 缺省指向仓库 `scripts/gh`（合并需要项目 PAT 的 Administration:write），systemd unit 模板写在脚本头注释；脚本不碰真实 runtime、不改仓库设置/密钥、不 kill 进程。best-effort（next/alpha）目标按方案决策 ③C 直接 exit 0、不建 PR，因为 manager 安装路径只装 max(地板, latest)。
## Alternatives considered

**在 GitHub Actions 里完成合并**——否决：CI 的 `GITHUB_TOKEN` 不能绕过分支保护，`--admin` 只有本机项目 PAT 能做；把 PAT 放进 Actions 是凭证面扩张，且 2026-09-22 已明文否决。**把 PAT 作为 secret 引入 CI（方案选项 A）**——否决：与零 secret 决策冲突，收益只是省一次本地合并。**在 autopilot 里重写安装逻辑**——否决：dsh-rehearse 的 install 场景已经验证过 warm store/软链/超时/探针，复制一份只会漂移。**字面执行 `gh pr checks --json`**——否决：本机 gh 2.45 直接 `unknown flag: --json`，改用方案允许的 `gh pr view --json statusCheckRollup`。**把 SKIPPED/NEUTRAL 当非 success 拒绝合并**——否决：PR 事件下 windows/linux/release 作业本来就 SKIP，按字面执行会让任何适配 PR 永不可合并；明确失败仍阻断。**版本 PR 无 check 直接合并**——否决：会掩盖将来可能出现的真 check；加了 head/文件白名单/静默期并显式记录例外。**无写域校验地合并版本 PR**——否决：白名单是 release-please bot 被篡改/行为变化时唯一的结构性防线。**构建失败自动重派发**——否决：Windows/Chocolatey flake 会造成无限重试；停在 ⑦ 并在 issue 说明，人去 Actions 重跑。**每次运行都 force-push auto 分支**——否决：会覆盖并发实例/既有 PR；只在无 open PR 且分支已存在时 force-with-lease，且锁到 ls-remote 看到的 sha。**加一个 resume 状态文件以支持 ⑤ 之后中断续走**——本轮否决：多一份跨会话状态与清理责任；先如实文档化「⑤ 之后中断/`--stage1` 需人工合并版本 PR」，等实际频繁发生再补。**把 autopilot 断言加进 `test-automation-gates.mjs`**——否决：本轮写域不含该脚本；改用 /tmp 的 27 条桩断言（GH_BIN/GIT_BIN/NODE_BIN/WATCH_JSON 注入）作为交付证据。
## Consequences

买到的是：一条命令/一个 timer 把「发现→适配→PR→CI→合并→版本 PR→构建→资产核验→issue 回帖」闭合，适配失败不留半截分支，同一 target 重跑不重复开 PR，发布后重跑幂等短路，所有失败都在 issue 里指名阶段与原因。代价与边界：版本 PR 自动合并意味着**零人工审阅**，唯一的结构性审查是写域白名单 + mergeable；release-please 版本 PR 的 checks 结构性不存在，不能声称「checks 绿」；进程在 ⑤ 之后中断（或 `--stage1`）不会自动续走——地板已等于 target，dsh-watch 不再报它，版本 PR 留在 open 需人工合并/派发；canary 默认关，开启时必须有窗口期内新启动的 dev 壳；next/alpha 不自动适配；资产 <3 停在 ⑦ 不自动重试；需要本机网络、SSH key 与项目 PAT。本轮只做了真实 dry-run（无新版，零仓库改动）与 27 条桩断言（覆盖 5 条负向 + 正向 CI 绿 + 已发布/重复 target/issue 复用/创建/canary/JSON），**没有对真实仓库执行任何 push/PR/合并/构建派发**，也没有跑真实的 rehearse+adapt+全量门禁串联；真实写路径仍是覆盖缺口。后续：若 ⑤ 之后中断变成常态，补 resume 状态；若能在写域内改门禁，把 autopilot 的负向对照并入 `test-automation-gates.mjs`；若 GitHub 未来对 bot PR 跑 workflow，重新评估 ⑥ 的例外。
