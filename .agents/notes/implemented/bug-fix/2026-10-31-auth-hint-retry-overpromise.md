# Agent Note: auth-hint-retry-overpromise

Status: implemented

## Problem

壳的「鉴权类误报提示」条幅在 AUTH 失败态承诺"若密钥确实正确，可直接重试本轮"，但 2026-10-31 设备级实测（Windows dev 壳 + 403 桩）证明：dsh 0.2.1-rc.5 在 AUTH 失败态只渲染 `Sixlwa_turnErrorCopy`（本轮运行失败 / API 密钥无效），全 DOM（含 shadow root、hover 后）没有任何 text/aria 含「重试/retry/重新生成」的控件 —— AUTH 不在 dsh 的可重试白名单，UI 本就不提供重试入口。壳的 `findRetryControl()` 按文本匹配必然落空，点「重试本轮」只得到 toast「未找到重试入口：请在失败的那一轮上点「重试」」——让用户去找一个不存在的入口，提示文案属过度承诺。

## Decision

保留条幅与按钮（成本低、对别的 dsh 版本/错误态仍可能命中应用内重试控件），把**文案改成用户真能执行的动作**，并加可失败断言：
- `misleadingAuthHint()` 返回改为「这也可能是上游瞬时故障（403/5xx 被误判为鉴权失败）；若密钥确实正确，可重新发送上一条消息。」——不再出现"可直接重试本轮"。
- 找不到应用内重试控件时的 toast 改为「未找到应用内重试入口：请重新发送上一条消息」。
- `scripts/test-shell-chrome.mjs` 新增两条断言：提示文案不得包含"可直接重试本轮"（对 2026-10-31 的设备级事实），必须包含"重新发送上一条消息"；既有措辞禁令（不得断言"不是密钥问题"）保持不变，因为壳依然分不清真密钥错与上游抖动。
- 仍然**不自动重试**（会掩盖真实鉴权错误、放大请求量）；按钮仍是 best-effort，只替用户点应用自己的控件。
## Alternatives considered

**删掉按钮只留说明**：否决 —— 别的 dsh 版本/其它错误态可能出现重试控件，按钮仍有价值，删掉是倒退；**实现"重新发送上一条消息"**：否决 —— 要处理附件/编辑/多轮上下文，且会改变应用自己的 turn 语义，超出提示层职责（可另立项）；**只改 toast 不改文案**：否决 —— 过度承诺在用户点按钮之前就已经发生；**改按钮标签为"重新发送"**：否决 —— 按钮点击语义是"找应用内重试控件"，标签与行为不符，且重新发送不是壳能可靠完成的动作。
## Consequences

买到：提示文案与真实可执行动作一致，用户不会再被引导去找一个不存在的重试入口；契约门禁现在锁住"不得承诺可直接重试本轮"，防止文案回退。代价与边界：① 按钮仍是 best-effort —— 在 AUTH 态它仍会走 toast（只是现在指引正确）；② 本次只改文案与 toast，**未重跑设备级验证**（条幅出现机制未变，上一轮已验证；如要闭环可复跑 §4.11 配方）；③ "重新发送上一条消息"依赖用户手动操作，壳不代发。
