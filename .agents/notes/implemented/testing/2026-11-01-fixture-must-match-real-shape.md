# Agent Note: fixture-must-match-real-shape

Status: implemented

## Problem

同一功能连续两次"测试全绿但真实环境完全不工作"：(1) 通知插件的测试桩在会话行对象上写了 `pendingInteraction`，而真实的 `SessionSummary` 根本没有这个字段，断言必然通过；(2) 用 `POST /state` 灌构造数据验证托盘 tooltip，证明的是"壳能显示我喂给它的东西"，而不是"数据能从 dsh 流到托盘"。两次都让我给出了错误的完成结论，代价是用户反复实测失败、排查数小时。

## Decision

fixture 必须从**真实类型定义**出发，而不是从被测代码的期望出发：凡是"某个字段应该存在"的假设，先在 dsh 源码里找到它的声明位置，再决定 fixture 把它放在哪里。状态类数据尤其要放在它真实所属的 observable 上——`running/pendingInteraction/completionUnread` 属于 `uiSession.sessionStatus`，不是列表行；测试里就必须有独立的 status store 桩，且行对象上**不能**出现这些字段（场景 31 显式断言 `!('pendingInteraction' in row)`）。<br><br>端到端验证必须走真实链路：构造数据只能证明**渲染层**正确，不能替代"生产者 → 传输 → 消费者"的验证；后者要么用真实会话，要么明确标注为未验证。Shell 侧的 `POST /state` 灌数据只算渲染单测，不算 E2E。<br><br>每条关键断言都要有**会失败的证据**：本次两处回归（数据源改回列表行、删掉 sessionStatus 订阅）都做了变异对照，确认失败的正是预期那条断言，而不是被别的错误带红。
## Alternatives considered

**让测试桩"方便地"承载状态**：写起来快，但它固定了一个真实不存在的契约，任何依赖该契约的实现都会被判为正确——这正是前两次翻车的直接原因。<br><br>**用构造数据 + 截图当作实机验收**：成本低、看起来像端到端，但它绕过生产者，无法发现"代码根本没被触发"这类问题（本次的 scan 未被唤醒正是如此）。<br><br>**依赖人工复测代替自动化**：用户实测确实是最终判据，但它只能是最后一公里；把可自动化的契约（数据形状、触发源）交给人工，会让每次迭代都以数十分钟的往返为代价。
## Consequences

测试成本上升：需要先读上游类型、构造两个 store 桩、并为关键路径写变异对照。换来的是失败能落在正确的层——本次最终定位到 `scan()` 从未被 `sessionStatus` 唤醒，正是靠"只改 status store、不动列表行"这一条场景 32 才可能被自动化抓住。<br><br>仍存在的缺口：真实会话的端到端（发起任务 → 进入待审批 → 托盘变化）无法在本机自动化，只能人工确认；`src-tauri` 的 Rust 侧没有单元测试覆盖 `build_tray_tooltip` 的字符预算收敛，目前仅靠实机观察，登记为覆盖缺口。
