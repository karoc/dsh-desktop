# Agent Note: dsh-upstream-release-day-drill

Status: implemented

## Problem

上游 dsh 发版是**不可控窗口期**：6h SLA 要求"发布后 6 小时内出稳定版"，但链路（dsh-watch / dsh-adapt / dsh-compat-probe / dsh-sla-report + 4 个 workflow）从未在"上游真的发版"条件下跑过完整推演。等窗口来了才发现"很多准备其实可以提前做"，正是要避免的失败模式。需要一套**不触发真实上游发布**就能把发版日走一遍的方法，以及各步骤的真实时间预算。

## Decision

本仓采用"桩 + 副本 + 临时 runtime"三件套做发版日演练，三者都**不修改已跟踪文件**。① **packument 桩**：dsh-watch.mjs 用 `execFileSync('curl', ...)` 取 packument，因此在 `.tmp-investigate/drill/bin/` 放一个只做 `cat packument.json` 的 curl 壳并把该目录前置到 PATH，就能让**未经修改的**真实脚本对着任意 dist-tags 跑；配合 `.tmp-investigate/drill/scripts/` 下的字节级副本（`sha256sum` 必须与仓库文件一致）与可 sed 的 MIN_DSH_VERSION 副本，即可穷举比较边界。这是当前**唯一**能演练比较逻辑的手法，因为 dsh-watch 的 registry URL 与地板来源都写死。② **临时 runtime 真装**：`--runtime-dir /tmp/rt-rehearsal`（空目录）+ `.pnpm-store` 与 `node_modules/pnpm` 软链到真实 runtime 的对应物，直接以真实参数启动 `scripts/server-manager.mjs`，走它自己的启动期自动安装路径（`if (!dshInstalled(...)) installDshUpdate()`）。实测把 `@deepseek-ai/dsh@0.2.1-rc.2` 真装成，安装段 103.8s（reused 522 / downloaded 36）。**绝不**指向真实 runtime。**2026-10-19 已固化为一条命令**：`node scripts/dsh-rehearse.mjs [--version <v>] [--keep] [--json <out>] [--timeout <sec>]`（扩展 `--warm-store <dir>` 换热 runtime、`--registry <url>` 透传）。它 `mkdtemp` 建空 runtime，只软链真实 runtime 的 `.pnpm-store` 与 `node_modules/pnpm`，用生产同款参数（`--runtime-dir/--resource-dir/--patch` + `--cwd <tmp>`）启动 manager 走**启动期自动安装路径**；到 `install-status done` 即按**进程组**终止（`detached:true` + `kill(-pid)`），实测 manager 从 done 到 `launching dsh web` 只隔 ~20ms，故正常都由该日志行这条"逃逸线"触发终止 —— 起 `supervise()` 起服务这件事被结构性地掐掉了（首轮手工配方正是没掐，才在临时 runtime 里真起了一个带 token 的 dsh web 并跑满 300s）。随后断言 `<tmp>/node_modules/@deepseek-ai/dsh/package.json` 的 version == 期望值且 `lib/bin.js` 存在，再跑 `--runtime <tmp>` 的兼容探针，最后打印每步耗时表 + 一行结论。退出码：0 全绿 / 1 演练失败 / 2 用法 / 3 前置（热 runtime 缺失等）；`--json` 写结构化结果（含完整指纹与探针 findings）。**`--version` 是期望值而非注入开关**——启动期路径的目标恒为 `max(壳地板, registry latest)`，不一致时如实报 `MISMATCH` 并 exit 1（配 best-effort `npm view` 诊断），绝不强行判绿。失败的运行**一律保留现场**（`--keep` 只影响成功的运行）。脚本每次运行都会打印三条 gap：只覆盖全新安装分支、只到探针（不验证 dsh web 能否真起来）、目标版本不可注入。③ **版本戳假 runtime**：`dsh-adapt` 第 1 步判据只是读 `<runtime>/node_modules/@deepseek-ai/dsh/package.json` 的 version 字段，故一个只含该单文件的目录即可通过——可用它演练"目标版本≠地板"时的分支行为，但它不证明安装可用（探针随后会因缺 dsh-web-app 判 RED，这是**正确**行为）。边界事实：manager 侧 registry **可注入**（`--registry` > `DSH_DESKTOP_REGISTRY` > npmjs）；dsh-watch / dsh-sla-report 侧**当时不可注入**（URL 写死）——**2026-10-19 已补上** `--registry`（两者）与 `--floor`（仅 dsh-watch，钉住地板），因此"PATH 劫持 curl 壳"不再是唯一手法，见 ../bug-fix/2026-10-18-dsh-upgrade-automation-defect-batch.md。时间预算是：安装 ~104s（非 Windows 宿主口径）> 23 套门禁 64.4s（其中 test-broken-install 32.6s + test-control-plane 29.2s 占 96%）≈ 探针 29.1s >> 夹具重采 0.93s ≈ 只读校验 0.95s >> peer 兼容 0.04s；CI 出包 ~10–11min（push 与 tag 运行同量级）。**演练明确不做**：不碰真实 runtime、不建 PR、不发版、不对真实 GitHub 写。
## Alternatives considered

**用本地 stub registry 装一个"假的新 dsh 版本"**——放弃：`@deepseek-ai` 家族 305 个包锁步同版本发布，手写 packument 无法复刻整族 tarball 与完整性哈希，缺的是整族制品而非脚本能力。**改仓库脚本加"演练开关"**——放弃：会在被测物上开洞，绿色不再可信；改为在 /tmp 与 .tmp-investigate 下操作字节级副本。**等下一次真实上游发版来验证**——放弃：窗口不可控，且这正是要避免的"临时抱佛脚"。**跳过探针的 --dry-run 深度选项**——放弃：那会把唯一的真实判据也关掉，属假绿。**整份复制 546MB node_modules 做临时 runtime**——放弃：软链 store/pnpm + 空目录已足够复现安装路径，成本低一个数量级。**（2026-10-19）把 bash 配方原样包一层**——放弃：会保留"跑满 300s + 每跑一次真起一个 dsh web + 从不清理"的语义，且没有断言就没有判断。**（2026-10-19）走 manager 的 stdin 命令通道指定版本**（`{"cmd":"update-dsh","version":v}` 确实支持）——放弃：它要求 manager 已进 `supervise()`（即已 spawn dsh 子进程）并触发 restart，演练对象从"启动期自动安装"漂成"运行中更新"，且多一次进程生命周期。**（2026-10-19）用本地 stub registry 注入要装的版本**——仍未实现（与本次交付的 `--version` 语义不是一回事）：整族 305 包锁步发布 + 完整性哈希，手写 packument 复刻不了制品；因此 `--version` 只表达期望值。
## Consequences

买到的：把"能不能提前演练"从推测变成已验证事实——装候选版本这一步**能**提前演练（实测 103.8s，而非代码注释里沿用的 31.9s，说明该常量是 Windows 宿主+全热 store 口径，跨环境引用会低估）；比较逻辑边界可用桩穷举，并据此抓出两个 P0（`watch` 的 `pre()` 对无预发布版本返回 `['']` 使三个 `length===0` 分支成死代码 ⇒ `cmp('0.2.1','0.2.1-rc.2')=-1`；manager 的 `preOrder` 让 `preOrder('0.2.1')=999 < preOrder('0.2.1-rc.2')=2002` ⇒ `updateAvailable=false`，两侧口径"一致地错"，rc→stable 转正这一最典型的发版动作会静默不触发）。代价与遗留：① 桩手法依赖 `PATH` 劫持 `curl`，属**旁路**而非脚本支持的注入点，脚本一旦改用 Node `fetch` 即失效——建议仍给 dsh-watch / dsh-sla-report 加 `--registry`（对本地 stub 已验证 2 行改动可行）。② `dsh-adapt --dry-run` **结构上无法**演练版本变更：它只跳过第 2/3/4 步，而这三步恰是唯一能消掉第 6 步探针 `version-vs-floor` / `version-vs-fixture` 两条 RED 的动作，故只要 target≠floor 必然停在第 6 步；能全绿的只有 target==floor 的幂等路径，那恰恰不是发版日。③ 临时 runtime 演练会拉起一个真实 manager+dsh 进程 —— **2026-10-19 起不再成立**：`dsh-rehearse.mjs` 在 `launching dsh web` 处按进程组终止（进程组同时覆盖 pnpm 与万一已 spawn 的 dsh 子进程），实测无 URL 事件、无残留进程（脚本内 `/proc/*/cmdline` 全扫 + 外部 `ps` 双证）；代价是**放弃了装完之后"dsh web 真能起来"这一段验证**，该段仍靠真机验收。另两条实测口径：安装段在**首次（store 未完全热）82–104s**、**store 全热后 27–33s** 之间浮动（上一笔记引用的 103.8s 属前一口径，跨环境引用仍会高估）；`--version` 不可注入这一结构性限制以 `MISMATCH` + exit 1 显式暴露，不再是静默行为。④ 未覆盖：`--canary` 实机验收需要 dev 壳在检查期间**新启动**（脚本只认启动后新增的日志行），本轮未跑；SLA 历史基线 0/7 达标、中位 47.62h，说明瓶颈在人工反应延迟（适配段中位 21.55h）而非机械流水线（本机全链 ~2min + CI ~11min）。相关笔记：../testing/2026-10-18-workflow-dry-run-audit-harness.md、../testing/2026-10-18-gate-negative-control-harness.md。
