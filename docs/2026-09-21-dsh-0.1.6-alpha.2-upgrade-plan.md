## 0. 结论摘要（先看这个）

1. **能升，而且壳的启动机制不用重写。** 探针证明 alpha.2 上 `dsh web --patch <overlay> --no-open --host 127.0.0.1 --port 0`
   照常启动，stdout 仍是 `dsh web: http://127.0.0.1:<port>/?token=…`（壳的 URL_RE/token 假设不变）；
   `--patch` 叠加行仍生效；复制进 runtime 的 4 个预装 bundle（含 scoped 的 `@karoc/…`）
   在 alpha.2 新增的 `runtime` + `enforce` 解析模式下**仍能解析并加载**。
   `[已验证: .tmp-investigate/probe-alpha2.sh 探针输出 + probe/dump.yml]`

2. **壳内插件管理确实可以整个删掉。** `@deepseek-ai/dsh-plugin-manager`（宿主侧服务）
   与 `@deepseek-ai/dsh-client-ui-plugin-manager`（Web 侧边栏 Plugins 页）是 **alpha.2 新增**
   （提交 `98b92b683c`，只有 tag `dsh-v0.1.6-alpha.2` 含它），且 `ui-plugin-manager` 已挂进
   `dsh-web-app` bundle → 壳组合出的 web profile **自带侧边栏 Plugins 页**。
   上游 Electron 桌面端做了同一个决定（删掉原生插件管理 renderer/IPC/包操作），
   并把"保留壳内独立插件管理页"作为**被否决的备选**写明了理由。
   `[已验证: git log/tag + packages/bundle/web-app/cordis.patch.yml:258 + dsh web --dump-config 输出]`

3. **壳侧必须新增的只有两处**（其余都是删除）：
   - 把内置 pnpm 挂到 **`dsh web` 子进程**的 PATH（今天只对 `dsh plugin` 挂）——
     否则 dsh 的插件页装不了插件；
   - 升级默认目标版本（npm `latest` 仍是 `0.1.5-rc.2`，**全新安装会装到没有插件管理的版本**）。

4. **会真实丢掉 3 项能力**（必须写进 README 的负向保证）：
   ① dsh 运行时不可用时管理插件；② 插件"更新到新版本"（新管理器只有安装/启用/停用/卸载）；
   ③ 预装插件的"从 npm 升级 / 恢复出厂版本"。

### 2.3 profile 与解析模式（本版本最危险的一处改动）

- `apps/cli/src/profile-boot.ts:263`：默认 `resolutionMode` 由 **`link` 改为 `runtime`**：
  - alpha.1：`packaged ? 'runtime' : options.resolutionMode ?? 'link'`
  - alpha.2：`packaged ? 'runtime' : options.resolutionMode ?? 'runtime'`
  `[已验证: git show dsh-v0.1.6-alpha.1:apps/cli/src/profile-boot.ts | grep resolutionMode]`
- `runtime` 模式下 `PluginPackages` 以 `behavior: 'enforce'` 装载（`profile-boot.ts:312-315`），
  由 Node 解析钩子强制把 profile 作用域内的模块解析到计算出的"解析代"上。
- **壳无法退回 `link`**：`resolutionMode` 只能由**进程内调用方**传（Electron 桌面端走
  `apps/desktop-host/src/index.ts:21` 的 `process.argv[5]`），CLI 不暴露 flag，也没有 `DSH_*` 环境变量。
  `[已验证: grep resolutionMode apps/cli/src；grep DSH_.*RESOLUTION 无结果]`
- **结论（探针实测）**：复制进 `<runtime>/node_modules` 的 bundle 属于 profile 的 bundle 层，
  `healProfileModuleFallback` 会为其依赖闭包建 profile 私有投影，bundle 本体按正常 Node 解析
  从安装目录找到 → **enforce 模式下仍可用**，4 个预装 bundle 全部加载（stderr 有 `[dsh-kanban]` 活动）。
  `[已验证: packages/boot/app-boot/src/profile.ts:719-760 + 探针]`

### 2.4 新插件管理（替换对象）

- 组合出的 web profile 里新增这些行（`dsh web --dump-config` 实测）：
  `plugin-manager`（服务）、`tool-plugin-manager`（agent 工具，默认 `disabled: true`）、
  `hmr`（新 `@deepseek-ai/dsh-hmr`，决定开关能否免重启生效）、
  `ui-plugin-manager`（侧边栏 Plugins 页）、`ui-settings-plugin-inventory`（Settings 只读清单）。
  `plugin-manager` 与 `hmr` 的启用条件是 `!!js '!ctx.get(''profileContext'')'` —— 壳用 CLI 启动 profile，
  条件成立，**两个都启用**。 `[已验证: probe/dump.yml:2-11, 504-507]`
- 能力：安装（先 `inspect` 校验 spec）、启用/停用 bundle、启用/停用 bundle 内的行、
  卸载（带确认）、安装进度/取消、pnpm 构建脚本审批（`pendingBuilds` + "允许并重试"）、
  插件自带配置页。写入位置：profile `package.json` 的 `dsh.profile.bundles` +
  `cordis.patch.yml` 的行级 `disabled`；有 HMR 时**免重启**生效。
  `[已验证: packages/boot/plugin-manager/README.md + src/index.ts]`
- **它没有"更新"操作**：`installBundle` 对已安装的 spec 直接 `refused('already-installed')`，
  Web 页也没有 update 动作。 `[已验证: src/index.ts:262-267；ui-plugin-manager/src/client 无 update 动作]`
- 对壳现有预装 bundle 的表现：`listBundles` 把 `dsh.profile.bundles` 里选中的名字都列出来；
  我们的 bundle 不在 profile `dependencies` 里 → `installed=false` → `removable=false`
  （能开关、不能卸载）。`[已验证: src/index.ts:194-221 源码推演；⚠ UI 实际呈现待实机确认]`

### 2.5 上游 Electron 桌面端的同一决定（最有力的先例）

`.agents/notes/implemented/architecture/2026-09-10-desktop-web-wrapper.md`：

- "The shared Web plugin manager owns installation, activation, errors, and restart requirements.
  **Electron has no separate plugin-management renderer, preload, shell asset route, plugin IPC,
  or package-mutation runner.**" —— 与我们这次要做的完全一致。
- 被否决的备选："**Keep a separate native plugin-management page.** It can operate while the Web Host
  is unavailable, but duplicates package operations, renderer IPC, localization, and backend restart
  handling. Native recovery already supports disabling third-party bundles and backing up the profile
  patch without the Host." —— 这正是我们壳内插件管理窗口的存在理由（dsh 崩溃时可用），上游明确不采纳。
- 上游仍保留的能力："Native recovery already supports **disabling third-party bundles** and
  **backing up the profile patch** without the Host." → 对应到我们：**"dsh 起不来时至少要能停用插件"
  这个安全网不能一起删掉**，见 §3.3。

  ③ manager 的预装/安装/更新/重置流水线（`dsh.json` 记 `preinstalled`/`updates`）。
  `[已验证: 读源码]`
- **dsh 自更新入口不止插件控制台一处**：壳菜单 `检查更新…`（`shell-chrome.js:50,75`）、

## 3. 升级方案

### 3.1 目标版本与通道（决策点 1）

**建议：给 dsh 设"最低版本地板" `MIN_DSH_VERSION = 0.1.6-alpha.2`，而不是钉死具体版本。**

- 目标版本 = `max(npm latest, 0.1.6-alpha.2)`：
  - 今天 `latest`=0.1.5-rc.2 < 地板 → 装 `0.1.6-alpha.2`（alpha 通道）；
  - 将来 `0.1.6-rc.1`/`0.1.6` 发布后 `latest` 超过地板 → **自动恢复**原有的自动更新行为；
  - 既保证"插件管理一定在"，又不把壳永久钉死在 alpha。
- 启动时加一道**兼容闸门**：已装 dsh < 地板 → 走现有的 `installDshUpdate({version})` 升级，
  并在启动页如实显示"正在升级 dsh 到 <版本>（当前版本缺少插件管理）"，失败则如实报错、不假装成功。
- 顺带修一个**现存的诚实性缺陷**：`installDshUpdate()` 的目标是 `latestVersion`，
  而"有更新"徽标只在 `latest > current` 时为真 → 今天的 alpha 用户（0.1.6-alpha.1）
  在界面上看不到 0.1.6-alpha.2 这个"next 可升"，只能靠插件控制台的预发布区。
  地板机制会顺带把这条路径打通。

**放弃的替代**：钉死 `0.1.6-alpha.2`（丧失自动更新）；把默认通道改成"全 tag 取最高"（用户被动吃 alpha 质量）。

### 3.2 壳侧必须新增（2 项，改动很小）

1. **`dsh web` 子进程 PATH 加内置 pnpm shim**
   （`server-manager.mjs` 的 `supervise()` spawn env，复用 `pnpmShimDir(runtimeDir)`），
   让 dsh 的插件页能真的装/卸载插件。需要同步 `src-tauri/resources/manager/` 副本（真源/副本契约）。
2. **最低版本地板 + 启动兼容闸门**（§3.1）。

| 插件版本"更新" | ✅ | ❌ | **能力损失**（退化为卸载+重装，或 `dsh plugin --profile web update`） |
| 预装插件从 npm 升级 / 恢复出厂 | ✅ | ❌ | **能力损失**（预装版本改回"随壳版本锁定"） |
| dsh 不可用时管理插件 | ✅ | ❌ | **能力损失**（用 §3.3-D 的安全网兜底） |
| 升级 dsh 本体 | ✅（控制台一区） | ❌ | **不损失**（壳菜单/托盘本就有） |

### 3.5 迁移与回滚

- **老用户**：`0.1.5-rc.2` / `0.1.6-alpha.1` → 启动时被兼容闸门升到 `0.1.6-alpha.2`。
  升级路径与今天一致（`pnpm install @deepseek-ai/dsh@<target>` + 插件备份/恢复 + profile bundles 快照恢复），
  **不需要改 profile 布局**（`profiles/web/` 的 `package.json`/`cordis.patch.yml`/`pnpm-workspace.yaml`
  在 alpha.1 就已是这个形状）。
- **回滚**：壳版本可回滚；dsh 回滚到 alpha.1 会让插件页消失（壳已无自建 UI）→
  回滚必须**同时**回滚壳版本，这条要写进发布说明。
- **风险点**：`0.1.5-rc.2` 用户在升级到 alpha.2 时跨了 1687 个提交，
  升级后必须实机验证（见 §4），不能只靠 CI。

## 6. 决策点（已拍板 2026-09-21）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 版本通道 | **采纳"最低版本地板 `MIN_DSH_VERSION = 0.1.6-alpha.2` + 保留自动更新"**：目标 = `max(latest, 地板)`；启动时低于地板走既有升级路径并如实显示进度 |
